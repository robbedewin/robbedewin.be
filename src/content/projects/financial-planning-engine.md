Belgian personal-finance advice is mostly generic, and the parts that are not —
the tax treatment, the pension projection, the succession rules — are the parts
that actually change the answer. I wanted to be able to produce a real,
numerically honest financial plan for a given household, and to be able to
regenerate last year's plan next year and get the same numbers back.

That turned into two projects that fit together.

## `market_data` — the store

A YAML registry declares instruments and factor sets: roughly 132 instruments
and 25 factor sets, each with its provenance. Fetchers pull from yfinance, the
ECB, the Ken French data library, AQR, Damodaran, Shiller, Goyal–Welch, Wikifin
and broker CSV exports, and write Parquet. DuckDB queries it. A small public API
(`md.get()`, `md.fx()`, `md.dividends()`, `md.factors`) and an `mdata` CLI
(`status`, `validate`, `health`, `explain`, `plot`, `snapshot`, `update`) sit on
top.

The feature the whole design turns on is `as_of=`. Every read can be pinned to a
date, so a report rendered today from last year's `as_of` reproduces last year's
numbers exactly. Without that, a "plan" is a screenshot of whatever the market
happened to be doing on the day it was rendered, and there is no way to tell a
modelling change from a price change.

## `financial_report` — the document

A per-household data bundle (`profile.yaml`, `holdings.yaml`, `transactions.csv`)
becomes a twelve-section plan rendered by Quarto to HTML and PDF: net worth,
investment policy, historical performance, benchmark and factor attribution,
cost analysis, pension projection, Belgian tax treatment, estate and succession,
rent versus buy, savings-account optimisation, and a recommendations section
that carries the numbers it is derived from.

Around it: a 90-test suite, GitHub Actions CI running ruff and pytest, a custom
Quarto theme (SCSS plus a Lua filter for section numbering) with a matching
matplotlib palette so the charts and the document are one design rather than two,
and a fingerprint-based cache so re-rendering only recomputes what changed.

## What I would tell you it taught me

The engineering lesson was that reproducibility is a data-layer property, not a
reporting one. I tried to solve it at the report level first — caching figures,
pinning versions — and it does not work, because the input keeps moving
underneath. Pushing `as_of` down into the store and making every read take it
was the change that made the rest of the system honest.
